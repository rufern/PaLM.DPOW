This section corresponds to transaction [LAB-104] of the IHE PaLM Technical Framework. Transaction [LAB-104] is used by the Image Manager / Image Archive (IMA), Physical Asset Workflow Manager (PAWM), and Digital Asset Workflow Manager (DAWM) actors. It is initiated using `OML^O21` and acknowledged with `ORL^O22`; common segment definitions are specified in the [Volume 2 Appendices](volume-2-appendix.html).

> **Editor's note:** The section number `3.LAB-104` uses the provisional transaction number as its section identifier pending formal IHE transaction number registration.

### 2:3.LAB-104.1 Scope

This transaction is used by the Image Manager / Image Archive (IMA) to notify the PAWM and the DAWM that a digital whole slide image is available in the image archive, or that a physical asset no longer has any available image (removal or de-association).

### 2:3.LAB-104.2 Actor Roles

<p id="t3LAB104.2-1" class="tableTitle"><strong>Table 2:3.LAB-104.2-1: Actor Roles</strong></p>

| Actor | Role |
|---|---|
| Image Manager / Image Archive (IMA) | Sends image availability or de-association notifications. |
| Physical Asset Workflow Manager (PAWM) | Receives notification. Updates slide status accordingly. |
| Digital Asset Workflow Manager (DAWM) | Receives notification. Updates case readiness status. |
{: .grid}

### 2:3.LAB-104.3 Referenced Standards

- HL7 v2.5.1: Chapter 4 (OML^O21, ORL^O22), Chapter 7 (SPM segment)

### 2:3.LAB-104.4 Messages

The process flow for this transaction is illustrated in [Volume 1, Use Cases #6 and #7](volume-1.html#overview) (image availability and de-association notification).

#### 2:3.LAB-104.4.1 OML^O21 - Image Availability Notification Message

##### 2:3.LAB-104.4.1.1 Trigger Events

- A whole slide image becomes available in the IMA.
- A physical asset no longer has any available whole slide image, because its last available image has been removed, de-associated, or flagged as faulty. No de-association notification is sent while at least one image remains available for the asset.

##### 2:3.LAB-104.4.1.2 Message Semantics

The message is `OML^O21`. MSH-21 SHALL be populated with `DPOW-IMAGE-NOTIF^IHE`.

`SPM-20` SHALL be used to convey image state:

- `Y` - image is available
- `N` - image has been de-associated or removed

`SPM-18` SHALL carry the **scan date/time** (the date and time the WSI was created by the scanner).

The IMA MAY include both the Study Instance UID and the Series Instance UID as OBX segments to allow the receiving actor to retrieve the image via DICOM/DICOMweb. Per DPIA (as amended by CP-LAB-279), all images from a single scan of a single slide share the same Series Instance UID.

> **Open Issue 9:** `OUL^R22` may be required as an alternative message type when result content (e.g., thumbnail, QC status) needs to be conveyed. This will be evaluated at Trial Implementation. See [Significant Changes and Issues](issues.html).

##### 2:3.LAB-104.4.1.3 Expected Actions

Upon receiving an image availability notification (`SPM-20 = Y`), the PAWM SHALL update the slide status. The DAWM SHALL update the case view and, if all expected slides for a case have images available, MAY transition the case to ready for pathologist review. A subsequent [LAB-101] Case Update with `ORC-1: SC` and `ORC-5: IP` from the PAWM signals that all images for the case have been imported (examination in progress).

For de-association notifications (`SPM-20 = N`), the PAWM and DAWM SHALL treat any previously available image(s) for the identified asset as no longer associated and clear any "images available" indication for that asset (for example, a slide-level flag in the LIS). De-association applies whether the underlying image was physically deleted or merely de-associated; DPOW does not distinguish the two. Implementations are expected to log de-association events, either through an application log or, for actors grouped with ATNA, as an audit event.

Each receiving actor then returns the `ORL^O22` acknowledgement described below.

#### 2:3.LAB-104.4.2 ORL^O22 - Acknowledgement

##### 2:3.LAB-104.4.2.1 Trigger Events

- Receipt of the `OML^O21` Image Availability Notification message by each receiving actor (PAWM and DAWM).

##### 2:3.LAB-104.4.2.2 Message Semantics

Each receiving actor returns `ORL^O22` as the application acknowledgement. MSA-1 conveys the acknowledgement code: `AA` (accept), `AE` (application error), or `AR` (application reject). When MSA-1 is `AE` or `AR`, an ERR segment SHOULD convey the error detail.

> **Validation required - see WI-DPOW-01.** The exact MSA/ERR usage is subject to message validation before Trial Implementation.

##### 2:3.LAB-104.4.2.3 Expected Actions

The IMA SHALL process each acknowledgement. On `AE`/`AR` the IMA SHOULD log the failure and MAY retransmit the notification to the affected actor.

#### 2:3.LAB-104.4.3 CapabilityStatement Resource

Not applicable. DPOW is an HL7 v2.5.1 messaging profile and defines no FHIR CapabilityStatements; actor conformance is defined by the HL7 v2 message and segment specifications above and in the [Volume 2 Appendices](volume-2-appendix.html).

### 2:3.LAB-104.5 Security Considerations

This transaction conveys PHI. All actors SHOULD be grouped with ATNA and the Consistent Time (CT) Time Client (see [Volume 1, Section 1:XX.5](volume-1.html#security-considerations)).

#### 2:3.LAB-104.5.1 Security Audit Considerations

##### 2:3.LAB-104.5.1.1 Image Manager / Image Archive (IMA) Audit

When grouped with an ATNA Secure Node or Secure Application, the IMA (sender) SHALL record an audit event when it sends a [LAB-104] message.

##### 2:3.LAB-104.5.1.2 Physical Asset Workflow Manager (PAWM) / Digital Asset Workflow Manager (DAWM) Audit

When grouped with an ATNA Secure Node or Secure Application, each receiving actor (PAWM and DAWM) SHALL record an audit event when it receives a [LAB-104] message.
